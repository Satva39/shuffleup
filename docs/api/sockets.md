# Socket.IO Reference

## Connection

Socket.IO connections must present the existing JWT as `handshake.auth.token`. The server verifies the token before accepting the connection and stores the authenticated user id on `socket.data.authUserId`.

The frontend uses one Socket.IO client created in `frontend/src/services/socket.js` with `autoConnect: false`.

The backend creates one Socket.IO server in `backend/src/server.js`.

## Central room events

### Client → server

| Event | Payload |
|---|---|
| `create-room` | `{ gameId, user }` |
| `join-room` | `{ roomCode, user }` |
| `toggle-ready` | `{ roomCode, userId }` |
| `start-game` | `{ roomCode, userId }` |
| `leave-room` | `{ roomCode, userId }` |

### Server → client

| Event | Purpose |
|---|---|
| `room-updated` | current room/player state |
| `game-started` | room moved into gameplay |

## Game socket modules

Every game registers its own namespaced input events and emits namespaced state/result/error events.

See `api/game-events.md` for the complete event-name inventory.

## Error acknowledgments

Where an event has a callback, game sockets generally return `{ success: true, ... }` or `{ success: false, message }`. Game error events use a namespaced `:<error>` event with a message payload generated by the corresponding socket module.

## Broadcasting

Game modules commonly send both room/public state and player-specific private state. Exact recipient selection is game-specific.
